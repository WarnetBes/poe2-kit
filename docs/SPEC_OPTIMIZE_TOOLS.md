# ТЗ: optimize-тулы poe2-kit (по паттерну MaxWilk poe2-build-mcp)

> Источник-эталон: `C:\TestPE\poe2-kit-DLS\mcp-rivals\MaxWilk\` (manifest.json v0.1.40, CLAUDE.md,
> pob_headless.lua). Лицензия MIT — приёмы переносимы, текст не копируем дословно без атрибуции.
> Статус: ТЗ, НЕ реализация. Реализация — по одному этапу, каждый с smoke-тестами.

## 1. Контекст и расхождение архитектур

- **MaxWilk:** headless-PoB движок (LuaJIT-субпроцесс через JSON-RPC stdio) = единственный
  источник чисел. 60+ тулов. Инвариант №1: «число, которое не выдал движок, не называется числом».
- **Наш kit:** TS/Node, движка PoB НЕТ. Есть: декодер PoB-кодов (build.ts), estimate.ts
  (приближённые EHP/DPS без PoB → ~80% AI-запросов), advice.ts, calculators (ehp/spirit/stun/
  resources — канон PoB2 выверен по исходникам), price-check, parse, poe2db/RePoE-датасеты.
- **Следствие:** любой оптимизатор у нас даёт *приоритеты и оценки*, а не точные PoB-числа.
  Правило для всех новых тулов (заимствован у MaxWilk, переработано под нас):
  **каждое число помечается `computed:` (формула/канон) или `estimated:` (эвристика).
  Пара «оценка → проверка в PoB» — обязательна в выводе тула.**

## 2. Инварианты (заимствовать из MaxWilk CLAUDE.md, адаптировать)

1. **Не выдумывать числа.** estimated-оценки — только через существующие канонические
   модули (ehp/resources/stun/spirit), не через новые «прикидки» в туле.
2. **Сервер — субстрат, не ИИ.** Тул отдаёт данные и оценки; синтез рекомендаций — работа
   модели. Никаких «умных» хардкод-эвристик в MCP-слое.
3. **Verify-before-present** (MaxWilk-норма `create → validate → cost → present`):
   сгенерированный вариант gear/passives обязан сопровождаться `validate:`-блоком
   (resists capped? атрибуты соблюдены? Spirit ≥ 0?) до вывода.
4. **Оптимизация — ограниченный перебор.** Все optimize-тулы обязаны иметь явные
   ограничения итераций/кандидатов (защита от комбинаторного взрыва в MCP-вызове).

## 3. Спецификация тулов (этапы)

### Этап 1 — read-only аудит (без мутаций, чистая свёртка наших данных)

| Тул | Что делает | Наши источники | MaxWilk-аналог |
|---|---|---|---|
| `poe2_evaluate_build` | Билд против числовых целей (DPS/EHP/резисты/Spirit): каждой цели — verdict + разрыв | build.ts (gear/stats из PoB-XML), estimate.ts, ehp.ts | evaluate_build |
| `poe2_rank_levers` | Ранжирование «рычагов» по маржинальному эффекту: +1 узел vs +гамильт flat vs +support — в единицах ΔEHP / ΔDPS-оценки | ehp/resources/stun + gem-датасет | rank_levers + list_levers |
| `poe2_pinnacle_check` | Чек-лист готовности к эндгейму: резисты/кап жизни/EHP-порог/устойчивость к stun — verdict per item | ehp.ts, stun.ts | pinnacle_readiness |

### Этап 2 — генерация кандидатов (мутации только в памяти тул-вызова, PoB-код наружу)

| Тул | Что делает | Ограничения перебора |
|---|---|---|
| `poe2_scaffold_gear` | Заполнить пустые слоты плейсхолдерами под цели (резисты→пул): сгенерировать PoB-item текст | 1 предмет, не набор |
| `poe2_craft_item` | BiS-рарка для слота: выбор баз + affix-набор по metric/weighted goals; отчёт по attainability (ilvl/tier из tradeQuery-специфик) | слот + metric, топ-5 аф fixes |
| `poe2_rank_upgrades` | Слоты по маржинальной выгоде перекрафта: сравнение «сейчас vs BiS-оценка» | по слотам, не по предмету |
| `poe2_plan_gear` | Наборgear: максимизация damage при капнутых резистах — бюджетное распределение по слотам | жадный алгоритм, 1 проход |

### Этап 3 — требует данных, которых нет (сначала данные, потом тул)

- `optimize_passives` / `alloc_passive` — нужен граф-роутер по TreeData PoB2
  (_research/path-of-building-poe2/src/TreeData есть, но парсер дерева — отдельный этап).
- `optimize_supports` — нужны числовые величины support-множителей по уровням камней
  (dataset/support gems). Сейчас голословно — НЕ ДЕЛАТЬ без данных.

## 4. Не заимствуем (осознанно)

- Headless-LuaJIT движок в рантайме: тяжёлый вендоринг PoB2 + чужая лицензионная зона
  (_research — только чтение). Наш вектор: канонические формулы по исходникам PoB2,
  отмеченные `computed:`.
- Corpus-SQLite: наши датасеты (poe2db.json, tradeQuery-специфик) уже покрывают read-часть.
- Эндпоинт `lookup_mechanic` (live-wiki): у нас уже есть poe2_wiki_lookup.
